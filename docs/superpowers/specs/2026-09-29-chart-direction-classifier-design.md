# 日足チャート × AI方向分類器（Phase 2） 設計

作成日: 2026-09-29（2026-09-29改訂: Opusサブエージェントレビューを反映）
ステータス: 承認済み（brainstormingセッションで全分岐を確定、レビュー後に採用基準等を修正）

## 背景

`docs/superpowers/specs/2026-09-24-stock-chart-forecast-design.md`（PR #21でマージ済み）で
実装した予測レンジは、ドリフト（直近120営業日の対数リターン平均の延長）＋ボラティリティ区間
（±1σ/±1.96σ、ホライズン20営業日）による統計的手法であり、ARIMA/Prophet/LSTM等のAI/ML手法は
意図的に不採用とした。理由は「日次終値のみを入力とした短期予測では、ドリフト付きランダム
ウォークが非常に強いベンチマークであり、これを安定して上回るモデルを作るのは容易ではない」
という設計判断（性能ではなく正直さの判断）。

同設計書には次の一文で将来タスクが明記されている:

> **Phase 2（別タスク）:** モメンタム・RSI・MACD・ボラを特徴量とした方向分類器を
> walk-forwardバックテストで検証し、方向的中率が有意に50%を上回った場合のみ
> 中心線を差し替える。勝てなければ採用しない。

本設計書はこのPhase 2を具体化するもの。目的（「今の株価が統計的にどのくらい異常かを可視化し、
統計的にどう動くかを把握できるようにする」「売買シグナルの提供ではない」）は前設計書から
変更しない。

**改訂の経緯:** 初版をOpusサブエージェントにレビューさせたところ、「採用基準の帰無仮説が
50%では、正のドリフトを持つ株価に対して『常にup』と予測するだけの無意味なモデルでも
有意に勝ててしまう」という指摘があった。検討の結果、比較対象を50%から**既存のドリフト
中心線自身の的中率**に変更した（対比較）。これによりPhase 2の本来の目的（「既存手法より
本当に優れているか」の検証）に忠実になる。あわせて、オーバーラップラベルによるp値の
過小評価・リーク・中心線差し替えの具体的な定義の欠落など、統計的な穴を修正している。

## 目的

日足の価格系列から算出した特徴量（モメンタム・RSI・MACD・ボラティリティ）を用いて、
既存の予測ホライズン（20営業日先）における方向（強気/弱気）をMLモデルで予測する。
ただし、walk-forwardバックテストで**既存のドリフト中心線に対して統計的に有意に優れている**
ことを示せた場合に限り、既存の中心線をこのモデルの予測方向に差し替える。優位性を
示せない場合は何も変更しない（過信を防ぐ、既存設計と同じ哲学）。

LLM（Claude API）による判定は採用しない。バックテストでの定量検証がしにくく、根拠が
言語モデルの推論に依存するため、既存の「点予測は過信を招く」という設計方針と衝突する
リスクがあるため。

## 設計判断

### 1. AI手法の選定

| 項目 | 決定 |
|---|---|
| 手法 | ML方向分類器（ロジスティック回帰） |
| 不採用 | LLM（Claude API）による判定、勾配ブースティング等の高自由度モデル |

**なぜロジスティック回帰か:** プール後のサンプル数が少ない（後述）ため、高自由度モデルは
過学習リスクが高い。まず最もシンプルなモデルで有意な優位性を示せるかを検証し、示せた場合に
限りモデルの複雑化を再検討する。

**新規依存関係:** `python-engine/pyproject.toml`には現時点でscikit-learn・scipyが存在しない
（fastapi/uvicorn/pydantic/pandas/pandas-ta/httpxのみ）。本機能の実装時に両方を追加する
（ロジスティック回帰・標準化にscikit-learn、二項検定/McNemar検定にscipy.stats）。Dockerfile・
`uv.lock`への影響があるため、既知の「Dockerfileベースタグ未pin」フォローアップと合わせて
確認すること。

### 2. 学習データの範囲

| 項目 | 決定 |
|---|---|
| プール方法 | watchlist全銘柄の(特徴量, ラベル)ペアを日付をまたいでプールし、単一のモデルを学習 |
| 不採用 | 銘柄ごとの個別モデル |

**なぜ個別モデルを採らないか:** `daily_prices`は銘柄ごとに最大約2年（約500営業日）しかなく、
watchlistはユーザーが自由に追加する少数銘柄の想定。銘柄ごとに個別モデルを学習させると
データ不足で過学習のリスクが高い。全銘柄プール型であれば銘柄数×日数分のサンプルが確保でき、
新規銘柄追加時も既存モデルですぐに推論できる。銘柄固有のクセは捕捉できないというトレード
オフを受け入れる。

**最小サンプル数ガード:** 独立観測数（後述の非重複サンプリング後の件数）が閾値
（暫定`MIN_INDEPENDENT_SAMPLES=60`、実装時に確定）未満の場合は学習・検定自体を実行せず、
`adopted=false`のまま何もしない。watchlistが1〜2銘柄・登録直後などデータが薄い状態で
無意味な判定が走ることを防ぐ。

### 3. ラベル定義・特徴量

| 項目 | 決定 |
|---|---|
| 目的変数 | 時点tにおいて、t+20営業日後の終値がtの終値より高ければ1（強気）、そうでなければ0（弱気） |
| ホライズン | 20営業日（既存の予測レンジ・中心線と同じ） |
| 特徴量 | 複数ウィンドウのモメンタム（リターン）、RSI、MACD、実現ボラティリティ |
| 特徴量の計算元 | 既存`app/services/indicators.py`のRSI/MACD計算を再利用。新規の外部データソースは導入しない |
| 特徴量のスケール | 価格水準ではなくリターン・比率ベースに正規化した上で標準化（平均0・分散1）。標準化のfitは学習フォールド内のデータのみで行い、検証フォールドにはそのパラメータを適用する（リーク防止） |

**なぜホライズンを既存と揃えるか:** 採用された場合に差し替える対象（予測中心線）が
20営業日先を指しているため、分類器の予測対象もこれに揃えないと差し替えの意味が
成立しない。

**なぜ特徴量の標準化が必要か:** MACD・モメンタムは価格水準に依存する単位を持つため、
全銘柄を価格そのままでプールすると株価水準の高い銘柄に重みが偏る。リターン化＋標準化で
銘柄間のスケールを揃える。

### 4. walk-forward検証と採用基準

**比較対象（帰無仮説）:** 「方向的中率が50%を上回るか」ではなく、**既存のドリフト中心線
自身の方向的中率と比較して有意に優れているか**を検定する（対比較、McNemar検定）。
理由: 日本株を含む多くの株価は歴史的に正のドリフトを持つため、「常にup」と予測するだけの
無意味なモデルでも50%を有意に上回ってしまう。Phase 2の本来の目的は「既存手法より本当に
優れているか」の検証であり、比較対象は既存手法（ドリフト中心線）でなければならない。

**walk-forward分割とembargo:** 時系列を複数の学習/検証フォールドに分割する。各フォールドの
学習データ末尾とそれに続く検証データの間に、ホライズン分（20営業日）のembargo期間を設け、
学習データのラベルが検証期間の価格を参照してリークすることを防ぐ。また「直近20営業日は
ラベルが未確定（t+20営業日の終値がまだ存在しない）」ため学習・検証のどちらにも使わない。

**オーバーラップラベルへの対策:** ホライズン20営業日に対し日次でラベルを生成すると隣接する
ラベルの19/20が重複し強く自己相関する。さらに全銘柄プールは同一日の市場ファクターの影響で
銘柄間相関も持つため、「銘柄数×日数」をそのまま独立試行として検定すると有意性を大きく
過大評価する。対策:
- 検定用の的中判定は各フォールドにつき非重複サンプリング（20営業日おきの時点のみ抽出）
  したうえで集計する（学習自体は全データを使ってよいが、検定はこのサブセットに対して行う）
- 上記に加え、モデルの学習には使わないネガティブコントロールテスト（方向を持たない合成
  幾何ブラウン運動系列を複数シードで生成し、同じパイプラインに通したときの採用率が
  有意水準α（0.05）にほぼ一致することをテストで検証する）を実装時のテストスイートに
  必須項目として含める。このテストが通らない場合、検定手法自体にバグがあるとみなす。

**採用基準:** 上記の対比較検定でp<0.05、かつ分類器の的中率がドリフト中心線の的中率を
上回る場合のみ「採用候補」とする。

**ヒステリシス（再検定の繰り返しによるα膨張対策）:** 24時間ごとに検定をやり直すと、
有意水準0.05のままではいずれ偶然「採用」と判定される回が発生する（多重検定問題）。
対策として、**直近N回（暫定N=5、実装時に確定）の再学習サイクルで連続して採用基準を
満たした場合にのみ`adopted`をtrueに切り替える**。一度`adopted=true`になった後は、
直近N回のうち過半数が基準を満たさなくなった場合にのみfalseに戻す（頻繁な切り替えに
よるUIバッジの点滅を防ぐ）。

**不採用時の挙動:** 既存のドリフト中心線をそのまま使用。分類器の結果はAPIレスポンスの
`adopted`をfalseにして返す（`hit_rate`/`p_value`自体は観測性のために返す、詳細は
セクション9）。

既存設計の「点予測は外れ方が見えないため過信を招く」という方針を踏襲し、検証に通らない
限り中心線には反映しない。

### 5. 統合先とAPI契約

| 項目 | 決定 |
|---|---|
| 計算場所 | python-engineに新規エンドポイント`POST /model/train`を追加（既存`/forecast`はそのまま） |
| `/forecast`への追加 | レスポンスに`direction_model`フィールドを追加。既存の`center`/`band`フィールドは形式不変 |
| `adopted=true`時の挙動 | センターラインの**符号（方向）のみ**を分類器の予測方向に合わせる。**大きさは変更しない** |
| go-api側 | `GET /stocks/{code}/chart`はレスポンスをそのまま透過（変更不要） |

**`adopted=true`時のcenter差し替えの具体的定義:** 分類器は方向（2値）のみを出力し、
値の大きさは推定しない。そのため差し替えは「既存のドリフト由来のcenter値の**絶対値は
そのまま**、符号だけを分類器の予測方向（`predicted_direction`）に合わせる」とする。
既存のドリフト方向と分類器の予測方向が一致する場合、`adopted=true`でも見た目上の
center値は変化しない。ボラティリティ帯（±1σ/±1.96σ）は新しいcenter値を基準に
再構成する（帯の幅=ボラティリティ由来の値自体は変更しない、中心だけがシフトする）。

`direction_model`のスキーマ:

```json
"direction_model": {
  "adopted": bool,
  "predicted_direction": "up" | "down" | null,
  "hit_rate": float | null,
  "baseline_hit_rate": float | null,
  "p_value": float | null,
  "trained_at": "2026-09-29T00:00:00Z" | null,
  "independent_sample_count": int | null
}
```

`baseline_hit_rate`（既存ドリフト中心線側の的中率）と`independent_sample_count`
（非重複サンプリング後の検定サンプル数）を追加し、`adopted=false`の場合の説明責任
（なぜ採用されていないか）を果たせるようにする。

**`POST /model/train`のリクエストスキーマ:** 銘柄ごとに日付付きの終値系列を渡す
（インデックス位置ではなく日付でフォールド境界を揃えるため。銘柄ごとに履歴の開始日・
長さが異なりうる）:

```json
{
  "stocks": [
    { "stock_code": "7203", "prices": [{"date": "2024-09-24", "close": 2500.0}, ...] },
    ...
  ]
}
```

ペイロードサイズは概算で銘柄数×500行程度（現実的なwatchlist規模では数MB未満）。
python-engine側のリクエストサイズ上限・タイムアウトは実装時にFastAPI/httpxクライアント
双方に明示的な値を設定する（既存`/forecast`呼び出しのタイムアウト設定を踏襲）。

### 6. モデルの学習・再学習トリガー

| 項目 | 決定 |
|---|---|
| 学習場所 | python-engine内、モジュールレベルのインメモリ状態（学習済みモデル＋検証結果＋直近N回の判定履歴） |
| 永続化 | しない（DB追加なし、MVP優先。python-engine再起動でリセットされる） |
| トリガー | go-api起動時に1回＋24時間間隔のティッカーで、watchlist全銘柄の価格履歴を集めて python-engineの`/model/train`を呼ぶ |
| 実装パターン | 既存`BackfillPriceHistoryUsecase.RunAll`と同じ形（goroutine、HTTPサーバーをブロックしない） |
| 新規usecase | go-apiに`TrainDirectionModelUsecase`を新設（domainパッケージに`DirectionModelTrainer`インターフェースを定義し、python-engineクライアントがそれを実装する。既存`forecast.Forecaster`と同じ依存方向） |

**なぜインメモリでDB永続化しないか:** モデル自体は素早く再学習できる規模（ロジスティック
回帰・全銘柄プールでも数百〜数千サンプル）であり、起動時＋定期バッチで再学習すれば
十分。永続化のための新規テーブル・マイグレーションを追加するコストに見合わない。この
判断はADR相当であり、実装時にADR-004（Go→Python同期HTTP）を補足するか新規ADRとして
記録することを推奨する。

**なぜ24時間間隔か:** watchlistの銘柄構成・価格データは日次更新（`MonitorUsecase`は
日次1回のポーリング）であるため、それより短い頻度で再学習しても新しい情報は増えない。
ただしティッカーは起動時刻起点の単純な24時間隔とし、日次ポーリングの完了タイミングとの
厳密な同期は行わない（許容する既知の制約。ずれても「やや古いデータで学習される」だけで
実害は小さい）。

**並行アクセスの安全性:** python-engineのFastAPIは同期`def`エンドポイントをスレッドプールで
実行するため、Goの`-race`検査は無効（Python側の話）。モジュールグローバルな学習状態への
書き込み（`/model/train`）と読み込み（`/forecast`）が同時に発生しうるため、`threading.Lock`
で保護する。また`/model/train`は多重起動に対して冪等（既に学習中であれば新規リクエストは
既存の学習完了を待つか、409を返して即座にスキップする）にする。go-api側が複数インスタンス
稼働する場合、同時に複数の`TrainDirectionModelUsecase`が起動しうる点も考慮し、python-engine
側の排他制御で吸収する（go-api側での分散ロックは導入しない、MVP優先）。

**デプロイ順序・再試行:** go-api起動時の初回呼び出しがpython-engine未起動等で失敗した場合、
既存の「1回失敗したらログのみで24時間待つ」は`BackfillPriceHistoryUsecase`の自己回復
パターンと比べて弱い。指数バックオフ付きで数回リトライする（例: 1分・5分・15分後）。
それでも失敗する場合はログを残し、次の定時サイクル（24時間後）まで待つ（既存の
「取得失敗はログのみで機能自体は止めない」方針を踏襲）。

### 7. 障害時・グレースフルデグラデーション

| 状況 | 挙動 |
|---|---|
| python-engine起動直後（学習前） | `/forecast`は`direction_model`の`adopted: false`・他フィールドは`null`を返す。フロントは既存のドリフト中心線をそのまま表示 |
| python-engineがクラッシュ・再起動 | モデル状態は消える。次の学習サイクルまで自動的に既存の統計手法にフォールバック（自己回復） |
| python-engine自体が応答不能 | 既存方針を維持（`forecast: null`で200、実績チャート・アラート境界帯は通常描画） |

既存の「PriceRepositoryバックフィルの自己回復」「Python engine障害時のフォールバック」と
同じ設計原則（自己回復・サイレント劣化を許容しつつ機能は止めない）を踏襲する。

### 8. フロントエンド表示

`adopted=true`の場合のみ、既存の「統計的期待レンジ」ラベル付近に小さなバッジを追加表示する。

- 表示例: 「AIモデルによる方向予測（過去データでの的中率XX%、既存手法比で統計的に有意）」
- 過信防止のため、**「この的中率は過去データでの検証結果であり将来の的中を保証しない」**
  旨の注記を併記する（既存の「予測はレンジであり点予測ではない」という既存注記と並べて
  一貫性を持たせる）
- `adopted=false`の場合は何も表示しない（過信防止、既存の「予測を取得できませんでした」
  パターンと同様に「出すべき根拠がない時は出さない」という方針を踏襲）

### 9. 観測性

`adopted=false`の場合でも`hit_rate`・`baseline_hit_rate`・`p_value`・`independent_sample_count`
はAPIレスポンスに含める（UIには出さないが、開発者がなぜ採用されていないかを確認できるように
する）。加えてpython-engineに`GET /model/status`（内部確認用、既存の認可方針に準拠し
watchlist所有権チェックの対象外である点を明記）を新設し、現在の学習状態・直近の判定履歴
（直近N回の採用可否）をJSONで返す。

## テスト方針

- python-engine:
  - 合成データでの分類器ユニットテスト（特徴量抽出・ラベル生成が正しいこと）
  - walk-forward分割ロジックのテスト（embargoが正しく効いていること、直近未確定ラベルが
    除外されること）
  - 非重複サンプリングによる検定サンプル抽出のテスト
  - McNemar検定の採用/不採用境界のテスト（p値・的中率差の閾値判定）
  - **ネガティブコントロールテスト（必須）**: 方向を持たない合成幾何ブラウン運動系列を
    複数シードで生成し、パイプライン全体を通したときの採用率が有意水準αにほぼ一致する
    ことを検証する。このテストは検定ロジックのバグ（p値過小評価等）を検出するための
    安全網として位置づける
  - ヒステリシス（連続N回判定）ロジックのテスト
  - `POST /model/train`・`GET /model/status`エンドポイントのテスト（既存`httptest`パターンに
    倣いモックデータ使用、多重リクエスト時の排他制御も含む）
  - `/forecast`が`direction_model`を正しく含む/含まない（未学習時）ことのテスト
- go-api:
  - `TrainDirectionModelUsecase`のテスト（既存`BackfillPriceHistoryUsecase`のテストパターンを
    踏襲、python-engineクライアントはモック、リトライ・バックオフのテストを含む）
  - 起動時1回＋定期ティッカーで呼ばれることのテスト
- 全体: `-race`必須（既存方針通り、Go側のみ。Python側の並行性はロックの単体テストで担保）

## 実装時に対応が必要な付随事項

- `python-engine/pyproject.toml`にscikit-learn・scipyを追加し、Dockerfile・`uv.lock`を更新する
- 新規環境変数（例: 再学習間隔、最小サンプル数閾値、ヒステリシスのN）をCLAUDE.md
  「環境変数（本番）」節に追記する（既知の「環境変数ドリフト」フォローアップと同種の
  抜け漏れを避ける）
- インメモリ学習状態の設計判断をADR-004の補足またはADR-008として記録するか検討する

## スコープ外（本設計では扱わない）

- LLM（Claude API）による判定・説明文生成
- 銘柄ごとの個別モデル
- モデルの永続化・バージョン管理・A/Bテスト
- go-api複数インスタンス間の分散ロック（python-engine側の排他制御のみでMVPを構成する）
- ロジスティック回帰以外のモデル（勾配ブースティング等）の検討は、優位性が実証された後の
  将来タスクとする
