# 株価チャート × 統計的期待レンジ 設計

作成日: 2026-09-24
ステータス: 承認済み（grillingセッションで全分岐を確定）

## 目的

**今の株価が統計的にどのくらい異常かを可視化し、統計的にどう動くかを把握できるようにする。**

売買シグナルの提供ではない。中心線は「直近のリターン平均を延長した線」に過ぎず、
レンジ帯は「よくある範囲」を示すものであって価格予測ではない。UIのラベリングも
この事実に従う（後述）。

## 背景（設計時点の現状）

- フロントエンドは `/login` `/register` `/watchlist` の3ルートのみ。チャートライブラリ未導入
- Go APIに価格を返すエンドポイントは存在しない
- 価格はRedis `price:<code>` に**日付なしの裸のfloat最大30件**のみ。日付は `lastdate:<code>` に最終日1件だけ
- 日付付き時系列を持つのは `YahooFinanceClient.FetchHistory`（`range=3mo` ハードコード、終値のみ）
- Postgresに価格テーブルは存在しない（users / watchlist / notifications のみ）
- Python engineはRSI/MACD/BBを価格リストから計算するのみ（最新1点だけ返す）

## 設計判断

### 1. 予測の性質

| 項目 | 決定 |
|---|---|
| 出力形式 | 方向＋レンジ帯（点予測しない） |
| 手法 | ドリフト＋ボラティリティ区間 |
| 中心線 | 直近120営業日の対数リターン平均を延長 |
| レンジ幅 | 日次リターンの標準偏差 × √h、±1σ（68%）と±1.96σ（95%）の二重帯 |
| ホライゾン | 20営業日 |

**なぜ点予測を選ばないか:** 日次終値のみを入力とした短期価格予測では、
ドリフト付きランダムウォークが非常に強いベンチマークであり、ARIMA・Prophet・LSTM等が
これを安定して上回らない。点予測は外れ方が見えないため過信を招く。

**Phase 2（別タスク）:** モメンタム・RSI・MACD・ボラを特徴量とした方向分類器を
walk-forwardバックテストで検証し、方向的中率が有意に50%を上回った場合のみ
中心線を差し替える。勝てなければ採用しない。

### 2. 「正常」の定義が2つ並立する問題

既存の異常検知（`anomaly/service.go`）は**終値の水準**のzスコアを使う
（直近30件の平均・標準偏差に対する現在値の乖離）。一方でレンジ帯は
**日次リターンのボラティリティ**ベースである。

**決定: 別物として並記する。**

- 過去区間の帯 = ローリング30日平均 ± `ANOMALY_THRESHOLD`σ（＝アラートが鳴る境界線そのもの）
- 将来区間の帯 = ドリフト＋ボラ×√h
- 凡例で「アラート境界」と「統計的期待レンジ」を明確に区別する

境界で帯の幅が不連続になるが、これを受け入れる。理由は、チャートがアラートの
説明責任（なぜ鳴ったか／鳴らないか）を果たせるのはこの形だけであり、かつ
既存の検知ロジックに手を入れずに済むため。

リターンベースへの統一は理論的には正しい（価格水準は非定常でzスコアが
トレンドに汚染される）が、Slackアラートの発火条件が変わり既存の通知履歴との
連続性も切れるため採用しない。

### 3. データ基盤

**決定: Postgres `daily_prices` に一本化し、Redis価格キャッシュを完全撤去する。**

理由:
- チャートには日付軸が要るが、Redisは日付を持たない
- ボラ推定には30件では足りない
- 2ストア併存は、Redisの値とdaily_pricesの値がズレた瞬間にチャートが嘘をつく
- `main.go` でRedisを使うのは価格キャッシュ1箇所のみ。撤去すると`REDIS_URL`・
  docker-composeのredis・CIの`redis:7`・RailwayのRedisプラグインが全て不要になる
- 既知フォローアップ「Redis価格履歴にTTLなし・陳腐化データで誤検知」が同時に解消する

| 項目 | 決定 |
|---|---|
| 保持期間 | 2年（`range=2y`、約500営業日） |
| デフォルト表示 | 6ヶ月。1M/3M/6M/1Y/2Y 切替 |
| 初期投入 | go-api起動時にwatchlist全銘柄を走査し、`daily_prices`が空の銘柄のみ逐次バックフィル（銘柄間にウェイト挿入、goroutineでHTTPサーバ起動をブロックしない） |
| 異常検知の窓 | 30件のまま変更しない（振る舞い不変） |
| 一意制約 | `(stock_code, date)` を主キーとし `ON CONFLICT DO NOTHING` |
| 銘柄削除時 | `daily_prices` は削除しない（再登録時の再取得コストを避ける） |

起動時バックフィルはwatchlistの銘柄数だけYahooへ連続リクエストするため、
逐次実行＋ウェイト挿入を必須とする。

### 4. 計算場所とAPI

| 項目 | 決定 |
|---|---|
| 予測計算 | Python engineに `/forecast` を新設（ADR-004の同期HTTP方針に従う。Phase 2のモデル・バックテストも同じ場所に積む） |
| チャートAPI | `GET /stocks/{code}/chart`（価格＋予測＋通知履歴＋現在zスコアを合成して返す） |
| 認可 | リクエストしたユーザーのwatchlistに無ければ404。データの存在範囲と認可範囲を一致させ、Yahooへの追加リクエスト経路を作らない |
| 障害時 | Python engine障害時は `forecast: null` で200を返し、実績チャートとアラート境界帯は通常描画する。「予測を取得できませんでした」と明示 |

### 5. UI

| 項目 | 決定 |
|---|---|
| 配置 | `/stocks/[code]` を新設。watchlist行クリックで遷移 |
| ライブラリ | Recharts（SVGベースでjsdomテスト可能、shadcnのchartコンポーネントが前提とする、Areaに配列dataKeyを渡すと区間の塗りが描ける） |
| 重ね表示 | 異常検知の発火履歴マーカー（`notifications`由来、ホバーでzスコアとAIレポート抜粋）＋現在zスコアの数値表示 |
| ラベル | 「統計的期待レンジ（68% / 95%）」とし、算出根拠（直近120営業日の対数リターンの平均と標準偏差）を注記で明示 |

RSI副チャートとボリンジャーバンドの時系列表示は今回のスコープ外
（Python `/analyze` が最新1点しか返さないため時系列対応の改修が必要）。
出来高も対象外（`fetchChart` が `close` しかパースしていない）。

## PR分割

性質が異なるため2つに分ける。

- **PR-A（基盤）**: Redis→Postgres一本化、2年バックフィル、起動時移行。
  **UI変更ゼロ・振る舞い不変**。単独でデプロイして検証できる
- **PR-B（機能）**: Python `/forecast`、Go chart API、`/stocks/[code]` ページ

混ぜると、本番でチャートがおかしく見えたときに「描画のバグか、データ移行のバグか、
検知ロジックの回帰か」を切り分けられない。

## 受容する既知リスク

- **銘柄追加がさらに遅くなる**: バックフィルが3mo（約60件）から2y（約500件）になる。
  `POST /watchlist` の同期ブロッキング解消は**独立したタスク**として切り出し済みで、
  本PRでは対応しない（Yahooへのリクエスト往復回数自体は1回のまま変わらず、
  増えるのはパース時間とDB書き込み件数）
- **マイグレーションは手動適用**: `003_create_daily_prices.sql` をRailway本番と
  ローカルの既存Postgresボリュームの両方へ当てる必要がある
- **予測がユーザーに過信される可能性**: ラベリングで緩和するが消せない
