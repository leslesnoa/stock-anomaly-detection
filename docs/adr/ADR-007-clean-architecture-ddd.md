# ADR-007: GoにClean Architecture + 実践的DDDを採用

**ステータス**: 承認済み  
**日付**: 2026-07-05

## コンテキスト

GoのAPIサーバーの内部設計として、テスタブルで責務が明確なアーキテクチャが必要。ポートフォリオとして設計力をアピールしたい。

## 決定

Clean Architecture の4層構成（domain / usecase / interface / infrastructure）と、実践的DDDのパターン（エンティティ・値オブジェクト・リポジトリインターフェース・ドメインサービス）を採用する。

**採用するDDDパターン:**
- エンティティ: User, Watchlist, Notification
- 値オブジェクト: AnomalyScore, ZScore
- リポジトリインターフェース: domainで定義、infrastructureで実装
- ドメインサービス: Z-score計算（anomaly/service.go）

**省略するDDDパターン:**
- 境界コンテキスト（単一サービスのため不要）
- ドメインイベント / Event Sourcing
- CQRS
- 集約ルート（規模に対してオーバースペック）

## 理由

- domain層が外部依存ゼロのため、ユニットテストが容易
- リポジトリインターフェースにより、テスト時にモックへの差し替えが可能
- 依存の方向が一方向（外側→内側）で、将来の変更に強い
- 境界コンテキスト等の厳密DDDパターンは7週間のスケジュールに対してオーバースペック

## DIの方針

`cmd/api/main.go` で依存を手動組み立て。Wire等のDIフレームワークは使わず、シンプルさを優先する。

## 不採用案

- **レイヤードアーキテクチャ（MVC）**: テスタビリティが低く、依存が双方向になりやすい
- **厳密DDD（ドメインイベント・CQRS含む）**: 設計コストが高く、7週間スケジュールで完成が困難
